# YouTube and Ads Analysis

An authenticated Model Context Protocol (MCP) server that lets ChatGPT retrieve reports from the owner's YouTube channel and Google Ads accounts. Account access requires Google authorisation and verification of the configured owner email.

## What is included

| Tool | Purpose |
| --- | --- |
| `check_connection` | Check the selected YouTube channel and directly accessible Ads customer accounts independently |
| `youtube_channels` | Selected channel metadata and lifetime counts |
| `youtube_videos` | Metadata and lifetime counts for known video IDs |
| `youtube_analytics` | Dated channel/video performance using the YouTube Analytics API |
| `youtube_reporting_jobs` | Existing bulk reporting jobs |
| `youtube_reporting_report_types` | Available bulk report definitions |
| `youtube_reporting_reports` | Metadata for report files generated by an existing job |
| `google_ads_customers` | Directly accessible Google Ads accounts |
| `google_ads_search` | Read-only Google Ads Query Language queries for account and campaign reporting |

The Reporting API tools currently list metadata. They do not create a reporting job or download its CSV files. Dated analysis is available through `youtube_analytics` after authorisation. If bulk exports are required, provision the desired Reporting API job separately and extend the connector to ingest its files. Enabling the API alone does not create those jobs.

## Access and authentication

The Google Cloud project must have YouTube Data API v3, YouTube Analytics API, YouTube Reporting API and Google Ads API enabled. Google Ads Explorer access is sufficient for the initial live-account reporting checks. As of 16 September 2026, Google Ads API access belongs to the OAuth application's Cloud project; this implementation does not require the retired developer token.

Google authorises the backend through a **Web application** OAuth client. ChatGPT separately obtains server-specific MCP access tokens through the backend's OAuth proxy. Google refresh tokens stay in an encrypted persistent store on the host. The Google client secret is not returned by the registration endpoint, and a Google access token cannot be used directly as an MCP bearer token.

The OAuth scopes are:

```text
openid
https://www.googleapis.com/auth/userinfo.email
https://www.googleapis.com/auth/youtube.readonly
https://www.googleapis.com/auth/yt-analytics.readonly
https://www.googleapis.com/auth/adwords
```

`openid` and `userinfo.email` identify the signed-in account so access can be restricted to `OWNER_GOOGLE_EMAIL`. The YouTube API scopes are read-only. Google's Ads scope is broad; this application enforces read-only behaviour by allowing only fixed metadata/report endpoints and never exposing mutation services. The Ads Search endpoint uses HTTP POST for a read request.

Google OAuth apps with an External audience and Testing status generally issue refresh tokens that expire after seven days for these scopes. Initial testing can use that status and the configured test user. A durable connection needs an appropriate publishing/verification status, subject to Google's requirements. Reconnect if Google revokes or expires the grant.

## Deployment settings

| Variable | Value |
| --- | --- |
| `PUBLIC_BASE_URL` | Actual public HTTPS origin assigned to this service, without a path or trailing slash |
| `GOOGLE_CLIENT_ID` | Google Web application OAuth client ID from the approved Cloud project |
| `GOOGLE_CLIENT_SECRET` | Its secret, entered directly into the host's private variable editor |
| `OWNER_GOOGLE_EMAIL` | The Google account permitted to use this connector |
| `TOKEN_ENCRYPTION_KEY` | A separately generated Fernet encryption key |
| `JWT_SIGNING_KEY` | A separately generated random secret, at least 32 bytes encoded as text |
| `TOKEN_STORE_DIR` | `/data/oauth`, on a persistent volume mounted at `/data` |
| `PORT` | `8000` |
| `MCP_REDIRECT_URIS` | Optional JSON array narrowing the documented ChatGPT callback allowlist to the exact URI shown by ChatGPT |

No production credentials are included. Keep the encryption and signing keys stable across deployments. Losing the token store or changing its keys requires reconnection. Back up the encrypted store and protect its encryption key separately.

For an existing connection that cannot open a new Google approval flow, an operator can temporarily set `AUTH_DIAGNOSTIC_ON_STARTUP=1`. On the next deployment, a bounded startup subprocess inspects the latest stored Google grant and reports only validation stages, status codes and boolean checks. It does not request consent, refresh a token, change stored grants or expose credentials. `AUTH_DIAGNOSTIC_CANDIDATE_EMAIL` optionally tests whether the verified account matches a proposed owner address; this comparison does not authorise that address. Disable the startup flag after collecting the result.

This diagnostic checks a saved Google grant, not the exact bearer token held by ChatGPT. A passing diagnostic alone does not prove that a plugin call will succeed. Diagnostic failures do not prevent the server from starting, and the subprocess is limited to 20 seconds.

The container initialises the token directory on the mounted volume and drops to UID/GID 10001 before starting the HTTP server. Deploy one replica with one worker. The file-backed token store is not configured for distributed concurrent replicas. A host without a persistent filesystem, such as an ordinary Cloud Run instance, needs a different persistent store before this application can be used reliably there.

The application fails to start if required settings are absent. Health status is available at `/health`; Google account information is not exposed there. OAuth discovery and consent endpoints are public. `/mcp` requires a valid server-issued token and the configured, Google-verified owner email. HTTP request logging is disabled to keep OAuth callback query strings out of access logs.

## Railway setup

1. Connect this repository to a Railway service. If a service has already been configured, reuse it to preserve the public origin, credentials and persistent volume.
2. Assign the service a public HTTPS origin and save that exact origin as `PUBLIC_BASE_URL`.
3. Create a Google **Web application** OAuth client with the authorised redirect URI `PUBLIC_BASE_URL` followed by `/auth/callback`. This is the backend's Google callback. Authorised JavaScript origins are not needed for this server-side flow.
4. Store the Google credentials and owner email in the service's private environment variables. Include all five scopes listed above in Google's Data Access configuration.
5. Generate separate random encryption and signing keys and store them in the service's private environment variables. For a fresh installation only, `python generate_secrets.py` creates keys locally in a private `.secrets.env` file and refuses to overwrite an existing file. Preserve existing keys when redeploying.
6. Attach a persistent volume at `/data` and configure `TOKEN_STORE_DIR=/data/oauth`. Railway charges for infrastructure separately from Google's API access.
7. Deploy using the included Dockerfile and `railway.toml`. Check `/health` and confirm `/mcp` returns an authentication challenge without a token.
8. In ChatGPT's MCP/plugin management UI, enable Developer mode if required and add the actual public origin followed by `/mcp`. Choose OAuth with dynamic client registration (DCR). The Google client ID/secret belong in the server's environment, not in ChatGPT's downstream OAuth client fields.
9. The server supports ChatGPT's documented stable callback `https://chatgpt.com/connector_platform_oauth_redirect` and callback-specific paths under `https://chatgpt.com/connector/oauth/`. The exact callback appears on ChatGPT's management page. For the narrowest allowlist, set `MCP_REDIRECT_URIS` to that exact URI before completing sign-in.
10. Connect, select the correct Google account/channel and grant the requested scopes. Start a new conversation with the connector available, run `check_connection`, and confirm the channel title/ID and the Ads customer ID before analysis.

Google may treat a YouTube Brand Account differently from the Google identity that owns Ads. The initial connection check deliberately checks both services independently. If one is inaccessible after choosing the intended channel, two separate Google authorisations may be necessary. Verify both services against the intended accounts after connecting.

## Local verification

Use Python 3.12:

```bash
python -m venv .venv
.venv/bin/pip install -r requirements-lock.txt
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest tests -q
```

The suite checks unauthenticated access, rejected identities and redirect destinations, MCP discovery, registration without leaking the Google secret, encrypted storage across reopening, the read-only tool catalogue, bounded Google requests, pagination/truncation and safe error handling. Google requests in those tests are mocked. Passing the suite does not prove live Google permissions, a selected Brand Account, host deployment or end-to-end ChatGPT connectivity.

## Measurement limits

Use the returned request context and all necessary pages when calculating totals. Ads monetary values ending in `micros` use one million units per account-currency unit. Retrieve the account's currency and timezone instead of assuming GBP or UTC. YouTube dated reports follow its Pacific time reporting conventions. Recent data and attributed conversions may change. YouTube creator advertising revenue is distinct from Google Ads spend; no creator-revenue scope is requested here. Channel views can include paid traffic, so they should not be labelled organic without a suitable filter.
